# 設計

## 方針

- 優先順位は「日本語入力の快適さ → 変換精度 → 応答と安定性 → サイズ・配置 → 編集操作 → iOSとの互換性 → UI → 追加機能」。
- 広告・課金・外部送信・AI機能（ネットワークを使うもの）は入れない。
- フルアクセスなしで全機能が動くようにする。フルアクセスで増えるのはクリック音と振動だけ。
- 変換は既存の優れたエンジン（AzooKeyKanaKanjiConverter）を使い、再実装しない。

## 構成

```
keyflow/
├── App/                     ホストアプリ（SwiftUI）: セットアップ、設定＋プレビュー、ユーザー辞書
├── Keyboard/                キーボード拡張: KeyboardViewController（UIInputViewController）
├── Packages/KeyFlowKit/     共有コード（Swift Package）
│   ├── KeyFlowCore          入力状態管理・キー配列・レイアウト計算・設定・保存（UIKit非依存）
│   ├── KeyFlowEngine        かな漢字変換（AzooKeyKanaKanjiConverterのラッパー）
│   ├── KeyFlowKeyboardUI    キーの描画・タッチ処理・候補バー（UIKit）
│   └── KeyFlowEval          変換精度・応答時間の評価ツール（アプリには入らない）
├── UITests/                 シミュレーターでの操作とスクリーンショット
├── eval/                    変換評価用のコーパスと比較スクリプト
├── scripts/                 IPA作成など
└── project.yml              XcodeGenの定義（.xcodeprojはCIで生成）
```

依存の向き: `App → KeyFlowKeyboardUI → KeyFlowCore`、`Keyboard → KeyFlowKeyboardUI, KeyFlowEngine → KeyFlowCore`。
アプリ本体は変換エンジン（辞書約40MB）を含まない。プレビューはひらがな・カタカナだけを返す簡易エンジンで動かす。

## 入力の流れ

```
タッチ（KeyboardView）
  → KeyAction（フリック方向・キー種別を確定）
  → InputController（入力中の文字列・候補・トグル状態を更新、入力欄へ即座に反映）
      → TextDocument（拡張ではUITextDocumentProxy、テストではSimulatedTextField）
      → ConversionQueue（バックグラウンドの直列キューで変換）
          → ConversionEngine（AzooKeyEngine）
      ← 候補（メインスレッドで受け取り、古い結果は捨てる）
  → InputViewState → 候補バー・キー表示を更新
```

### 文字を欠落させないための設計

- 入力欄への反映（marked textの更新）はキー操作と同じタイミングで同期的に行う。変換を待たない。
- 変換はバックグラウンドの直列キューで行い、連打中に溜まった要求は最新のものだけ処理する。結果は要求IDで照合し、古い結果は捨てる。
- 「変換」キーを押した時点で候補が届いていなければ、その場で同期的に変換して待つ（数ms）。
- 複数の指で素早く打ったとき（ロールオーバー）は、後の指が触れた時点で前の指の入力をその時点の方向で確定する。順番の入れ替わりを防ぐ。
- 候補タップは、表示中の候補一覧の要求IDと現在の要求IDが一致するときだけ受け付ける。

### 外部からの変更の検出

入力中にユーザーが入力欄をタップしてカーソルを動かすと、ホスト側でmarked textが確定される。
そのまま入力を続けると文字が重複するため、外部の変更を検出して入力中の状態を捨てる。

- 自分の操作の直後（0.5秒以内）に届いた`textDidChange`/`selectionDidChange`は自分の操作によるものとみなし、その時点の文脈を「期待する状態」として記録し直す（`adjustTextPosition`などは文脈の更新が非同期なため）。
- それ以外の通知は外部の変更とみなす。念のため`unmarkText()`を呼んでから状態を捨てる（ホスト側にmarked textが残っていると、次の入力で上書きされて文字が消えるため）。
- 通知が届かなかった場合に備え、次のキー入力の前にも文脈を確かめる。

この判定は実機で検証が必要（docs/PROGRESS.md の実機確認項目）。

### marked text

既定では入力中の文字列を`setMarkedText`で下線付き表示する（標準キーボードと同じ）。
アプリによって表示が崩れる場合に備えて、通常の文字として挿入・置換するモードも用意した（設定「入力中の文字に下線を付ける」）。

## キー配列

12キー（かな）:
```
[ ◀ ] [ あ ] [ か ] [ さ ] [ ⌫ ]
[ ▶ ] [ た ] [ な ] [ は ] [空白]
[ABC] [ ま ] [ や ] [ ら ] [改行]
[☆123][小゛゜][ わ ][、。?!][    ]
```
- ◀▶: 入力中は入力中の文字列の中でカーソルを動かす（カーソルより前だけを変換するので、文節の区切りを変えられる）。入力中でなければ入力欄のカーソルを動かす。トグル入力中の▶は標準キーボードの「→」と同じく文字を確定し、◀は1つ前の文字に戻す。
- 小゛゜: タップで巡回（か→が、は→ば→ぱ、つ→っ→づ）。左フリックで濁点、上で小文字、右で半濁点。入力中でなければ、確定済みの直前の1文字に適用する。
- 、。?!: タップ「、」、左「。」、上「？」、右「！」、下「…」。
- や: 左「「」、右「」」（SimejiやazooKeyと同じ。標準キーボードは「（」「）」）。
- 空白: 入力中は「変換」→「次候補」。予測候補は飛ばして変換候補だけを巡回する。横にドラッグするとカーソル移動。
- 地球儀キーはホームボタンのある機種（`needsInputModeSwitchKey`がtrue）でだけ表示する。

英字はQWERTYと12キー（フリック）を選べる。12キーでは文字を入力欄に直接入れ、トグルは入力欄の直前の文字を置き換える。「a/A」で直前の英字の大文字・小文字を切り替える。
数字・記号は12キーのフリック。候補バーの顔アイコンから記号・顔文字の一覧を開ける。

### 再変換

- 確定直後: 候補バーの「取消」で読みに戻し、選び直す。
- 選択したテキスト: 選択すると読みを推定して（iOSの`CFStringTokenizer`）、候補バーに読み全体の変換候補を出す。候補をタップすると選択範囲を置き換える。

## レイアウト

`LayoutEngine`がキーの矩形を計算する（UIKit非依存、テストあり）。
- キー間の隙間に触れても最寄りのキーが反応するよう、判定範囲を隙間の半分ずつ広げる。外周のキーは画面端まで広げる。
- 片手モードは指定した側に寄せ、空いた側に「反対側へ」「終了」ボタンを置く。
- 横画面は中央に寄せて幅を絞る（既定78%）。

## 設定と共有

- 設定は`KeyboardSettings`（Codable）。欠けたキーは既定値で補い、範囲外の値は丸める。
- アプリはApp Groupに書き込み、キーボードは読む（フルアクセスなしでは書き込めない）。
- キーボード上の調整パネルで変えた値はキーボード自身の領域に保存し、更新時刻が新しい方を使う。
- App Group IDは、Info.plistの値→署名に埋め込まれたプロビジョニングプロファイル→AltStoreの`ALTAppGroups`の順に探す。署名ツールがIDを書き換えても動くようにするため。
- 学習データはキーボード自身の領域（Library/KeyFlowLearning）に保存する。アプリからの消去は「依頼」をApp Groupに書き、次にキーボードを開いたときに実行する。

## 変換エンジン

`AzooKeyKanaKanjiConverter`をmainの特定コミット（04ce2ec, 2026-10-18）に固定している。
最新タグ v0.11.2 より辞書が新しく、評価コーパスで1位正解率が81%→85%に上がったため（eval/README.md）。

- Zenzai（ニューラル変換）は使わない。キーボード拡張のメモリ上限が厳しく（非公式の報告で48〜77MB）、モデルで数十MB増えるため。
- 予測候補は`manualMix`で受け取り、「入力全体の変換の1位 → 予測（最大3件）→ 残りの変換」の順に並べる。
- 文節の候補を確定すると、残りを入力中のまま続ける（`setCompletedData`で左文脈を渡す）。
- 確定後は次の語を予測する（`requestPostCompositionPredictionCandidates`）。直前の確定を置き換える種類の予測は、入力欄の書き換えが必要になるため使わない。
- 辞書は最初の変換時に読み込む（表示を遅らせないため）。メモリ警告を受けたら変換器を捨て、次に使うときに作り直す。
- 上流のmainには、予測時に`print`するデバッグ出力が残っている。動作への影響は小さいが、次に固定コミットを上げるときに確認する。

## フィードバック

- 押下時の色の変化は常に行う（指を置いた瞬間に反映）。
- 振動は`UIImpactFeedbackGenerator`。フルアクセスが必要な可能性が高い（Appleの記載なし）。
- クリック音は`UIDevice.playInputClick()`。フルアクセスと、iOS側のキーボードのクリック設定が必要。

## iOSの制約（実装しない・できないもの）

詳細は docs/research/ios-keyboard-constraints.md。

| 機能 | 状態 | 理由 |
|---|---|---|
| ペーストボタン | 実装しない | `UIPasteboard`の読み取りにフルアクセスが必要。プライバシーを優先し、入力欄の長押しメニューを使ってもらう |
| テキスト選択・全選択 | 不可 | 公開APIなし |
| 編集メニューを開く | 不可 | ホストアプリの機能 |
| 作文ツール | 不可 | キーボードから起動するAPIなし。選択時のメニューから使う |
| 音声入力 | 不可 | 拡張はマイクを使えない |
| カーソルの上下移動 | 不可 | APIなし。左右移動とドラッグで代替 |
| パスワード欄・電話番号欄 | 不可 | システムが標準キーボードに切り替える |
