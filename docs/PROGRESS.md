## 検証結果

### Linux（2026-10-21）
- `swift test`: 93件成功（入力状態管理・タッチ処理・レイアウト・設定・保存・エンジン・変換の補正・通し動作）
- `tools/uikit-typecheck/run.sh`: キーボードUIと拡張のコードがUIKitの簡易スタブで型検査を通る
- 変換評価（130文）: 1位 87%、3位以内 93%、10位以内 97%、学習1回後の1位 97%（docs/EVALUATION.md）
- 1打鍵の変換時間: 平均 2.3 ms、95%点 5.4 ms（x86_64 VM）

### iOS（GitHub Actions, Xcode 26.3 / Swift 6.2.4, 2026-10-22）
- シミュレーターでKeyFlowをシステムのキーボードとして登録し、実際のキーボード拡張で次を確認（UIテスト4件すべて成功）
  - フリック入力→変換→確定で「今日はいい天気」
  - 入力中に入力欄をタップしても、文字が重複・消失しない（「あいう」）
  - ダークモードの配色、横画面での表示と入力
  - ローマ字（QWERTY）で「kyouhaiitenki」→「今日はいい天気」
- テスト中のキーボード拡張のメモリ（シミュレーター、vmmapのPhysical footprint）: 最初は43MB→最大約90MBまで増えた
  - 変換エンジンを表示のたびに作り直していたのを1つにまとめた（ヒープ上のエンジンは1つ、解放漏れのコントローラーなしを確認）
  - 主因は候補の数だった。エンジンが1打鍵ごとに180〜350件を返し、候補バーがすべてにセルを作っていた（セル867個）。80件までにして、最大約68MBになった
  - 実機の値はこれと異なる（シミュレーターにはシステムライブラリの分が含まれる）
- 端末向けビルド成功、IPA作成（約16MB）。App Groupの権限情報が埋め込まれていることを確認
- シミュレーターでパッケージのテスト（変換エンジンを含む）がすべて成功
- UIテスト: アプリ内プレビューで、フリック入力（タップ・上/左フリック・小゛゜）、変換・次候補・確定、トグル入力、英字・数字への切り替え、ダークモードを操作・撮影
- UIテストで、英字・数字キーを押したときにアプリが落ちる不具合を見つけて修正（キー配列の切り替え中にタッチの一覧が空になり、範囲外アクセスになっていた）
- iOSで初めて分かったビルドエラー3件を修正（CoreGraphicsの読み込み、CFLocaleの作り方、変換の点数がarm64ではFloat16）

## 未完了・今後の改善

### 実機確認のあとに判断するもの
- 外部変更の検出（0.5秒の判定時間）の調整
- 振動がフルアクセスなしで動くか
- 既定の高さ・フリック判定距離の微調整（実際の指で決める）
- メモリ使用量（Instrumentsが使えないので、長時間使用で落ちないかで判断）

### 未実装
- キーボード内の簡易クリップボード（フルアクセス不要の範囲）
- Zenzai（ニューラル変換）: 必要メモリ約150MB（上流の資料）がキーボード拡張の上限を超えるため見送り。実機でメモリに余裕があれば再検討

### 既知の問題
- 上流（AzooKeyKanaKanjiConverter main）に予測時のデバッグ出力（`print`）が残っている
- アプリ内プレビューは辞書を持たないため、変換候補はひらがな・カタカナだけ
